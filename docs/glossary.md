# 翻译术语表与前缀缓存

服务端可在启动时加载完整 TSV 术语表，为当前 Hy-MT2-1.8B Q6_K 翻译提供指定译法。表中所有语言的全部条目都会按模型推荐的逐行术语句式编码为固定提示前缀；程序不做按词检索、预先纠错或条目筛选，原词、译词的大小写与词界由模型理解。

文件上传翻译和实时逐段翻译共用这份配置。客户端只需发送音频和目标语言，不需要在每次请求中上传术语表。术语表要求 LLM 优先遵从指定译法，不执行强制文本替换，也不改变 ASR 原文；仅识别接口不应用术语表。

## 准备 TSV 文件

使用 UTF-8 编码，每行按以下顺序填写三列，列之间使用一个实际的 Tab 字符：

| 列 | 含义 | 示例 |
| --- | --- | --- |
| `source` | 原词或短语 | `语音识别` |
| `target_language` | 该译法对应的目标语言 | `en`、`ja` |
| `translation` | 希望优先使用的译法 | `speech recognition`、`音声認識` |

[示例术语表](../examples/glossary.tsv) 内容如下。下方分隔符为 Tab，不是空格：

```tsv
语音识别	en	speech recognition
语音识别	ja	音声認識
本地	en	on-device
```

同一个原词可为不同目标语言配置译法。`target_language` 表示翻译输出语言，不是原音频语言。程序规范化目标语言代码，但保留所有条目；即使当前目标为 `en`，上例的 `ja` 行也会留在固定提示中，由模型结合当前目标语言理解。

加载后保留完整 canonical TSV，并将所有唯一条目转换为「原词翻译成指定译法」的逐行表达，附上与当前中文翻译指令一致的完整语言名称。这些行一起放入同一条 user 消息的固定前缀，不是把原始 TSV 原样拼入提示。上例对应的参考数据为：

```text
目标语言 英语："语音识别" 翻译成 "speech recognition"
目标语言 日语："语音识别" 翻译成 "音声認識"
目标语言 英语："本地" 翻译成 "on-device"
```

原词和译词使用 JSON 字符串转义，避免引号混淆；条目内容不删减。每次翻译的变化后缀明确本次目标语言，提醒模型只应用该语言的指定译法，同时仍传入全部语言的完整前缀。普通翻译指令还追加逐句完整保留数字、单位、条件和否定关系的提醒，不增加思考过程；提示基于官方模板，但经过项目调整。

文件支持 LF 或 CRLF 换行，可在文件开头包含 UTF-8 BOM。首个非空、非注释行可选用 `source`、`target_language`、`translation` 三列表头。空行、仅包含 ASCII 空格的行，以及不含 Tab、去除前导空格后以 `#` 开头的注释行会跳过。

字段首尾空白会去除，各列必须非空，不能包含额外的 Tab、换行、控制字符、方向控制符或模型控制标记。原词和译词保留大小写，例如 `US` 与 `us` 是两个不同的原词；这是加载时的完整性检查，不是按当前原文筛选术语。同一原词和规范化目标语言的相同译法会合并；出现冲突译法时，启动失败并报告行号。全部有效唯一条目按文件顺序保留，空表不能启用。

## 启动时加载

从源码项目根目录启动：

```powershell
.\target\release\streamtrans.exe --glossary .\examples\glossary.tsv
```

发行版可以指定单独维护的文件：

```powershell
.\streamtrans.exe --glossary C:\StreamTrans\glossary.tsv
```

`--glossary` 接受相对或绝对路径。不指定时不启用术语表。表在服务启动时完整读取一次并常驻内存，后续翻译不重复读取文件。修改或替换 TSV 后，需重启服务才能加载新内容；重新连接录音客户端不会刷新术语表。

## 容量检查

| 限制 | 行为 |
| --- | --- |
| 文件大小 | 最多 8 MiB，用于限制读取和解析的资源消耗 |
| 数据行数量 | 最多 10000 行，重复数据行也计入；不代表模型能容纳这么多条目 |
| 单行与字段 | 单个物理行最多 4096 字节；`source` 最多 512 字节，`translation` 最多 2048 字节 |
| 目标语言 | 最多 64 个字符，只允许字母、汉字、空格和连字符 |
| 术语表模型 token | 默认最多 1024 token，`--glossary-max-tokens` 可设为 1–4096；按实际模型分词结果检查 |
| 完整上下文 | 固定前缀、目标语言、当前原文和输出预算共同受 `--context-size` 限制；默认 4096 token |

1024 token 上限计算规范化后的完整 canonical TSV，包含固定表头；不是检查逐行术语句式的 token 数。程序另外对实际渲染后的完整固定前缀分词，检查该前缀、`--max-tokens` 输出预算及至少 512 token 的原文空间能否共同放入上下文。逐行表达、语言标签和指令都会占用前缀 token，不能用 TSV token 数代替实际前缀长度。提高 `--glossary-max-tokens` 不会扩大模型上下文，也不会绕过这项检查。更换模型后，必须由新模型重新分词和检查；旧 MiniCPM5 的 token 数不能用于推算 Hy-MT2 的容量。

表格格式有误、超出文件或条目限制、实际 token 数超限，或上下文空间不足时，服务明确报错并停止启动。程序不会裁剪、筛选或静默省略术语。需要减少术语表内容、调整输出预算，或使用服务支持范围内的上下文配置后重新启动。

每次翻译仍需检查当前目标语言和原文的实际 token 数。热缓存不能使超出上下文的内容变得可用；原文过长时不能靠重新发送同一请求解决。

## 缓存复用的范围

启用术语表后，服务在启动时读取完整 TSV 一次，对包含全部逐行术语表达的 user 固定前缀分词，保存前缀 token ID，并校验前后缀的 token 边界。后续每次翻译只对明确目标语言的指令、原文和模板尾部构成的后缀分词，再与已保存的前缀 token ID 拼接。切换原文或目标语言不会重新筛选或删改前缀条目。

请求使用 `cache_prompt=true`，由托管的 llama.cpp 单个推理 slot 复用共同前缀的 KV。首次翻译建立这份推理缓存，后续请求可复用仍然有效的相同前缀；服务重启、模型重新加载或缓存状态变化后，需要重新建立。token ID 缓存减少重复分词，KV 缓存减少重复计算，两者是不同的缓存。

当前本机 `/completion` API 仍要求每次传入完整的 token ID 序列，包括术语表前缀。这不是真正的网络零重传，也不是将术语永久写入模型。KV 仍占用上下文和 GPU 显存；实际复用程度以托管 LLM 的 `timings.cache_n` 为准，服务日志和翻译基准中对应 `cached_prompt_tokens`。

未启用术语表时，使用 Hy-MT2 的普通翻译提示和 `cache_prompt=false`。当前模型直接生成译文，不提供思考模式开关。术语表不更改原文，也不自动缩短输出预算；完整输入与输出预算超过上下文时明确报错。

新模型完整性、指定译法遵从和速度结果见 [Hy-MT2 复测](hy-mt2-20261103.md)。

这套提示改善了部分专名与指定译法，但没有消除所有语言影响。例如日语请求仍可能输出仅在英语条目中指定的 `on-device`。完整性提醒也不能保证数字边界、条件或否定全部正确；实际使用仍需按原文核对，不应把正常 EOS 或缓存命中视为质量通过。

## 历史 MiniCPM5-2B 实测（2026-11-01）

以下记录来自 MiniCPM5-2B Q4_K_M，不代表当前 Hy-MT2 的分词容量、缓存耗时或术语遵从率。Windows、RTX 3050（6 GB）上，当时使用完整 101 条术语表和空思考翻译配置进行验证。规范化后的 TSV 为 1015 个模型 token，在默认 1024 上限内；加上系统提示后的固定前缀为 1160 token。

独立翻译基准中，模型加载和内置预热耗时 1184.883 ms，术语编码及前后缀边界校验另耗时 5.616 ms。对同一句原文先请求一次，再连续请求 3 次：

| 指标 | 首次请求 | 3 次热态请求 |
| --- | --- | --- |
| 完整提示 token | 1189 | 每次 1189 |
| `cached_prompt_tokens` | 0 | 每次 1188 |
| 实际计算的提示 token | 1189 | 每次 1 |
| prefill 耗时 | 430.809 ms | 中位数 13.456 ms |
| LLM 总耗时 | 533.804 ms | 中位数 111.138 ms |

这里的 LLM 总耗时不包含 ASR、模型加载或术语表初始化，不能作为完整音频请求耗时。记录位于开发工作区 `.tools/benchmark/glossary-capacity-20261101.jsonl`。

同一个真实音频服务进程中，依次执行批量英语翻译、批量日语翻译，再执行 2 段英语 WebSocket 翻译，缓存统计如下：

| 请求 | 缓存 token / 完整提示 token |
| --- | --- |
| 批量英语 | 0 / 1196 |
| 批量日语 | 1167 / 1197 |
| WebSocket 英语第 1 段 | 1167 / 1190 |
| WebSocket 英语第 2 段 | 1172 / 1186 |

这验证了更换原文、目标语言及接口后仍可复用完整术语前缀。缓存还可能包含相同的模板或原文开头；程序不会把上一请求的原文或译文追加成当前请求的对话历史。随后仅识别请求返回 `200`、`translation: null`、翻译耗时 0 ms，LLM 调用次数未增加。对应材料为 `.tools/benchmark/glossary-server-20261101.log`、`glossary-http-*-20261101.json` 和 `glossary-stream-en-20261101.jsonl`。

容量检查另使用 500 条术语表，实际分词为 6008 token，超过 1024 上限后明确拒绝，未筛选或裁剪；错误记录为 `.tools/benchmark/glossary-overflow-20261101.err`。

另用专名表测试时，模型采用了「星海计划 → Project Aurora」「冥王星 → Hades」。但「本地 → on-device」在实测中仍被译为 `local`，没有遵从指定译法。这些样本验证了术语提示可生效，也显示它不是硬约束，不能保证每条译法都会采用。记录为 `.tools/benchmark/glossary-proper-names-20261101.jsonl`、`glossary-cache-en-20261101.jsonl`。

## 检查结果与排查错误

1. 检查服务是否以 `--glossary` 加载了预期文件；文件修改后重启服务。
2. 启动失败时，先检查 UTF-8 编码、三列 Tab 分隔、目标语言格式及日志中的容量错误。
3. 检查请求的目标语言和实际译文。所有条目都交给模型，不提供严格强制替换、词汇纠错或译文质量保证。
4. 需要检查缓存时，对比首次与后续翻译的 `cached_prompt_tokens`，将模型加载、分词和推理时间分别记录；缓存命中不代表上下文容量增加。

仅部署在服务端的术语表无需复制到录音客户端。制作分发包时只携带示例文件；业务术语表应由部署者另行维护和传入，避免把内部术语随通用软件包分发。
