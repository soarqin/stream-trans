# Hy-MT2 Q6_K 翻译完整性与响应速度

2026-11-03，Windows x64、Ryzen 7 5700G、RTX 3050（6 GB）。默认翻译模型已改为 **Hy-MT2-1.8B Q6_K**，继续使用随包携带的 llama.cpp b11960。ASR、FSMN-VAD、音频协议和客户端无需更换，不引入 Python，也不把模型权重放入分发包。

在本次定向语料中，新模型改善了单位、时间、对象及长段条件的翻译，但没有普遍提速，日语长段尤其更慢；仍存在遗漏、边界差异、表达歧义，以及多语言术语混用。下面将正常结束、语义核对和处理速度分开记录。

## 模型与最终配置

模型来自 [Tencent-Hunyuan 的 ModelScope 仓库](https://modelscope.cn/models/Tencent-Hunyuan/Hy-MT2-1.8B-GGUF)，固定 revision 为 `e97e6af0ec0950385644d7c0a8e5c899071f722b`。文件 `Hy-MT2-1.8B-Q6_K.gguf` 大小为 `1474785120` 字节，SHA256 为 `d98fe604dec1f28f58f80d7d560f7177e584d3b8e5835862687660e5ff97cb40`。Rust 下载路径和 SHA256 校验已经验证，旧 MiniCPM 文件及清单保留。

最终配置为上下文 4096、完整输出预算 2048、FP16 KV、Flash Attention 自动选择、CUDA0 全层加载。日志确认 LLM **33/33 层 offload**，ASR 仍为 CUDA0 BF16，FSMN-VAD 在 CPU 运行。

采样采用 [Hy-MT2 模型卡](https://huggingface.co/tencent/Hy-MT2-1.8B-GGUF) 推荐的温度 `0.7`、Top-P `0.6`、Top-K `20`、重复惩罚 `1.05`；项目固定 seed `42`，min-p、presence 和 frequency 惩罚均为 `0`。重复惩罚覆盖当前完整输入和输出，不继承上一句历史。b11960 的 HTTP 接口不接受 CLI 的 `repeat_last_n=-1`，请求使用当前提示长度加输出预算的非负窗口。

使用该权重自身的聊天模板和 EOS `120020`，不复用 MiniCPM 的控制标记或思考前缀。普通翻译基于官方中文指令，追加通用完整性要求：

```text
将以下文本翻译为 {目标语言}，注意只需要输出翻译后的结果，不要额外解释。请逐句完整翻译，保留所有数字、单位、条件和否定关系，不要概括或省略：

{完整原文}
```

术语表按完整条目转换为模型推荐的逐行译法表达，标明中文目标语言名，并在当前请求中明确目标语言。全部语言和全部条目始终保留，不按原文检索或筛选。固定前缀一次分词并复用 KV，容量规则见 [术语表说明](glossary.md)。当前不提供思考模式开关。

## 测试方法与比较边界

[固定语料](../examples/translation-cases.jsonl) 共 15 条：12 条不带术语表的核心用例，以及 3 条携带同一份 [完整 5 行词表](../examples/translation-glossary.tsv) 的用例。覆盖中英日翻译、日期时间、单位、否定条件、列表、标识符，以及 318/327 字符的长段和独特末句。原文及目标语言在两模型之间一致；每例首轮一次，再重复三次，保留每次完整译文和实际 token 统计。

语料由本次编码助手合成，并由助手按 106 项事实逐项阅读核对；没有独立人工标注、外部评测或词面自动评分。这是定向回归，不能作为总体翻译质量分数。

旧 MiniCPM 对照使用切换前冻结的 Release 程序、Q4_K_M 权重及默认空思考前缀。旧采样为温度 1、Top-P 0.95、Top-K 40、重复惩罚 1。两模型的硬件、运行时、上下文、输出预算、KV 精度和 seed 相同；提示和分词器分别使用模型对应实现。普通请求均禁用提示缓存。

另将 Hy-MT2 采样全部对齐旧值跑了同一批核心语料，结果未出现普遍提速：长段英译热态中位数 3.896 秒，日译 5.987 秒；旧模型分别为 3.246、4.064 秒。该辅助组使用未追加完整性提醒的原始指令，作为采样控制记录，不能冒充最终生产配置。不同模型生成长度和分词器不同，不能只比较 token/s，也不能把更短的漏译输出视为等价完成。

所有推理测试保持 GPU 单任务；模型加载及内置预热单独计时。没有清空操作系统文件缓存，因此“首轮”不是冷磁盘测试。Hy-MT2 最终核心组加载及内置预热为 **1185 ms**，随后首个真实翻译为 **208 ms**，同句三次热态中位数为 **202 ms**。早期独立进程加载及预热曾为 2212 ms，均未计入下表。

## 完整译文的响应速度

以下均为 LLM 总耗时，包含分词、prefill、解码和后处理，**不含模型加载、ASR 或音频传输**。每个数值是相同原文三次热态请求的中位数，最终 Hy-MT2 使用上面的完整性提醒。

| 用例 | 目标 | MiniCPM5 Q4_K_M | Hy-MT2 Q6_K | Hy 译文 token |
| --- | --- | ---: | ---: | ---: |
| 今天下午三点开会 | 英语 | 170 ms | 202 ms | 13 |
| 多日期与会议时间 | 日语 | 883 ms | 930 ms | 68 |
| 温度、压力、用量、误差 | 英语 | 960 ms | 957 ms | 70 |
| 充电条件与警报 | 日语 | 1067 ms | 1479 ms | 108 |
| 三项清单和最后交钥匙 | 英语 | 955 ms | 989 ms | 72 |
| 人名、版本和 API 标识符 | 日语 | 1171 ms | 1369 ms | 101 |
| 跨午夜 UTC 备份 | 中文 | 941 ms | 913 ms | 66 |
| 设备、电池和信封交付 | 中文 | 924 ms | 1069 ms | 77 |
| 百分点与退款阈值 | 英语 | 1125 ms | 1064 ms | 78 |
| 发言归属与修复承诺 | 日语 | 1117 ms | 1458 ms | 108 |
| 318 字符交接长段 | 英语 | 3246 ms | 4103 ms | 293 |
| 327 字符维护长段 | 日语 | 4064 ms | 6144 ms | 427 |

长段最终输出中，MiniCPM 分别生成 247/312 个译文 token，Hy-MT2 为 293/427；分词器不同，这些计数不能换算成等价字数。两者都保留了独特尾句，但新模型修正了旧输出中的多处信息错误。此次切换的收益主要是这些内容改善，不能宣称速度升级。

## 完整性核对

最终 15 条用例的 60 次请求均正常 EOS 结束，没有达到输出或上下文上限。这只验证技术上的完整结束，不等同于语义没有遗漏。

核对中的具体改善包括：

- 日译中的中午 12 点由旧输出的 `午前12時` 改为 `正午12時`，未获批准时沿用原安排的条件也更明确。
- 英译中的 MPa、升、毫秒、摄氏度均完成翻译，旧输出曾保留部分中文单位。
- 冷藏车、每箱抽取两只传感器、维护的 00:20 时间、先通知陈禾而不直接重启等事实得到修正。
- 最终长段保留 Q-731、紫色温度计、第四层抽屉、海鸥四十七、绿色卡片、六号柜和“不是 74”等尾部信息。
- 初始 Hy 指令曾将“恰好 40 笔不暂停”翻出相反含义；加入通用完整性提醒后，这条样本恢复了不暂停的极性，但 `it doesn’t stop` 的指代仍不自然，不能据此宣称所有否定问题已修复。

最终仍发现以下限制：

- “高于 30%”被译为“30％以上”。这是 `>` 与 `≥` 在恰好 30% 时的边界差异，**不是否定反转**；日常口语可能混用，此处按明确数值条件记录。
- “提高 9 个百分点，不是提高 9%”保留了前半解释，但省略了明确的“不是 9%”对照。
- 长段日译的“3 段各 10 秒”写成不自然的 `3セクションずつ10秒間`，数量作用域不够清楚，未据词面数字齐全判为完全准确。
- 三条固定术语用例采用了全部 6 项指定译法，但真实音频日译仍出现 `on-deviceのspeech recognition`，没有采用表中日语 `音声認識`。完整表进入提示和 KV 命中均已确认，多语言术语隔离仍由模型理解，不能保证每次采用正确语言的译法。

## 真实音频接口与连续输入

同一最终服务进程加载完整 5 行术语表，启动至就绪为 5501 ms，包含缓存 SHA256 检查、VAD/ASR/LLM 加载、LLM 内置预热和术语准备，单独记录，不计入请求。以下使用既有 WAV，没有录制麦克风。

| 9.122 秒中文文件的顺序请求 | HTTP | VAD+ASR | 翻译 | 处理总耗时 |
| --- | --- | ---: | ---: | ---: |
| 英语翻译，首请求 | 200 | 710 ms | 433 ms | 1180 ms |
| 日语翻译，随后请求 | 200 | 327 ms | 472 ms | 837 ms |
| 仅识别，随后请求 | 200 | 329 ms | 0 ms | 365 ms |

以上为单次请求，不是中位数；没有对齐冷/热 ASR，不作前后速度比较。仅识别返回 `translation: null`；英文、日文均包含两句原文及对应译文，日文术语混用如上所述。

WebSocket 按 1× 实时速率连续发送 PCM，客户端不跑 VAD：

- 9.122 秒音频返回 2 段原文、2 段日译和 `done`；首段译文在 5.806 秒收到，早于 `finish`，末段正常冲刷。
- 60.037 秒密集短句返回 22 段原文、22 段英译和 `done`，完成于 60.492 秒。没有错误，所有段推理排队等待为 0 ms；逐段翻译调用为 189–243 ms，最终 37 ms 短尾计入总时长。

这些结果证明该回放负载没有持续积压，不代表所有长句、语种或长时间录音都能跟上输入。

## 大术语表与截断保护

5 行表的 canonical TSV 为 53 token，实际固定前缀为 128 token；启动分词和 en/ja/zh 边界校验为 4.800 ms。三条术语用例后续请求成功复用前缀 KV，仍完整传入全部表条目的 token ID，不是网络零重传。

另用完整 101 条表验证容量和缓存。canonical TSV 为 1015 token，但逐行提示前缀为 1666 token：默认上下文 4096、输出 2048、原文预留 512 共同超限，启动明确拒绝。**没有自动缩小输出预算或裁剪词表。** 显式设置 `--max-tokens 1536` 后，同一完整表加载成功：提示 1742 token，首请求计算 1742，随后每次缓存 1741、实际计算 1；prefill 从 512.022 ms 降至热态中位数 14.682 ms。这组只验证容量和缓存，不能与默认 2048 输出预算的模型性能表混算。

完整 500 条表实际需要 6008 token，超过默认 1024 cap 后明确拒绝。原文过长或实际前缀超出上下文，也会报错，具体限制由完整上下文决定。

将输出预算故意设为 8 后，基准四次均记录失败，译文为 `null`，没有用失败结果生成成功耗时。真实音频接口返回 **502 `translation_failed`**，保留已识别原文和分段，报告 `stop_type=limit`，不把部分生成当成完成的翻译。

## 复现与验证材料

从项目根目录构建并回放合成语料：

```powershell
cargo build --release --example bench_llm --locked
$model = 'models/models/Tencent-Hunyuan--Hy-MT2-1.8B-GGUF/snapshots/e97e6af0ec0950385644d7c0a8e5c899071f722b/Hy-MT2-1.8B-Q6_K.gguf'
$caseLines = [IO.File]::ReadAllLines((Resolve-Path .\examples\translation-cases.jsonl))
[IO.File]::WriteAllLines('translation-core.jsonl', [string[]]@($caseLines | Where-Object { ($_ | ConvertFrom-Json).id.StartsWith('core-') }), [Text.UTF8Encoding]::new($false))
[IO.File]::WriteAllLines('translation-terms.jsonl', [string[]]@($caseLines | Where-Object { ($_ | ConvertFrom-Json).id.StartsWith('glossary-') }), [Text.UTF8Encoding]::new($false))
.\target\release\examples\bench_llm.exe --server .\dist\StreamTrans\runtime\llama\llama-server.exe --model $model --cases .\translation-core.jsonl
.\target\release\examples\bench_llm.exe --server .\dist\StreamTrans\runtime\llama\llama-server.exe --model $model --cases .\translation-terms.jsonl --glossary .\examples\translation-glossary.tsv
```

前两条写文件命令仅按固定用例 ID 分出测试组，保留每条原文和其余字段。这不是翻译时筛选词表；若直接对全部 15 条启用术语表，须标为另一组，不与本文核心组混算。

工作区 `cargo test --workspace --all-targets --locked`：**88 项通过、4 项真实 VAD 本地模型测试默认跳过**；格式检查及工作区 Clippy `-D warnings` 通过。已有客户端、仅识别、错误处理、完整表容量、KV 统计和流式队列回归通过。Linux、其他 GPU、真实麦克风采集和数小时录音未在此次验证。

原始材料保留于开发工作区 `.tools/benchmark/hymt2-completeness/`：`minicpm-all.jsonl`、`hy-final-core.jsonl`、`hy-final-glossary.jsonl`、`hy-matched-sampler.jsonl`、逐项语义核对报告、`http-final-*.json`、`ws-final-*.jsonl`、`http-truncation.json`、容量记录和 `final-tests.log`。普通最终基准使用冻结的 `hy-completeness-benchmark.exe`，之后仅调整术语路径，普通指令字节不变；术语组与接口使用最终构建。
