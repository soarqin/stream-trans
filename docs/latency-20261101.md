# 连续录音积压与翻译延迟复测

本文使用 MiniCPM5，保留为 2026-11-01 的历史记录。2026-11-03 起默认翻译模型为 Hy-MT2-1.8B Q6_K；本文的空思考开关不再适用于当前版本，新的完整性与响应速度测试见 [Hy-MT2 验证](hy-mt2-20261103.md)。

文中提到的开发工作区 `.tools` 测试记录和音频不随运行包分发。

2026-11-01，Windows x64、RTX 3050（6 GB）。本次针对连续录音报 `audio_buffer_full`、逐句延迟增加，以及短句翻译思考耗时过长进行调整。没有录制麦克风，音频使用已有中文样本处理后按实时速率回放。

## 旧版复现

单独发送 2.23 秒快速多词中文，再加 2 秒静音，旧版正常完成，未报缓冲区满。短句本身的词数不会改变相同采样格式下的音频字节数；这个测试不能代替用户当时的设备和连续录音现场。

另将「今天下午三点开会。」加速至约 1.92 秒，每句后加 0.85 秒静音，按 1 倍实时速度连续发送。旧版在 37.420 秒、已发送 37.400 秒音频时返回 `audio_buffer_full`。每句 ASR 约 110–113 ms、翻译约 3.8 秒，单次推理没有逐轮变慢，但结果越来越落后于录音位置：第 8 段在音频 21.090 秒结束，其译文直到测试开始后 34.235 秒才收到。

旧版在 ASR 和 LLM 推理期间停止读取原始音频队列，也不继续执行 VAD。已经结束的前一段返回了译文，仍可能有后续采样尚未交给 VAD。队列上限 12.8 秒只是错误阈值，不能单凭它确定任意一次短句报错的原因。

已核对 transcribe.cpp v0.4.1 的 [运行入口](https://github.com/handy-computer/transcribe.cpp/blob/v0.4.1/src/transcribe-asr.cpp)及 [FunASR Nano 实现](https://github.com/handy-computer/transcribe.cpp/blob/v0.4.1/src/arch/funasr_nano/model.cpp)：每轮清理输出及 KV 上下文。LLM 请求仅携带当前段原文，禁用 prompt 缓存，并检查服务端 `cache_n=0`。本次没有发现逐轮累积对话上下文的问题。

## 翻译思考策略

默认使用当前固定 GGUF 模板的空思考前缀 `<think>\n\n</think>\n\n`，让模型直接生成译文。`--llm-thinking` 可恢复原先的完整思考前缀。输出总预算仍为 2048 token，保留 EOS、截断和控制标记检查；没有用压低总输出上限制造提速。

固定权重的 `tokenizer.chat_template` 含 `enable_thinking=false` 分支，但 [OpenBMB 的部署文档](https://github.com/OpenBMB/MiniCPM/blob/main/docs/deployment/transformers.md#generation-defaults)将 2B 的 Think 列为受支持模式。因此空思考前缀作为本项目的低延迟翻译策略，需要用实际语言和语料评估质量；不能视为官方对 2B 非思考质量的保证。

## 冷热分离的同文本对照

原文为「今天下午三点开会。」。每种目标语言、每种策略各运行一个新 llama.cpp b11960 子进程，独立记录模型加载及内置预热、进程首请求，再取同进程 3 次热请求中位数。不清除操作系统文件缓存；没有同时运行其他 GPU 测试。

双方均使用同一份 `MiniCPM5-2B-Q4_K_M.gguf`、CUDA0 全层加载、4096 上下文、2048 输出上限、FP16 KV、Flash Attention 自动、`seed=42`、`temperature=1.0`、`top_k=40`、`top_p=0.95`，禁用 prompt 缓存。唯一主动改变的是思考前缀，因此输入 token 也随之改变；不声称前后提示词 token ID 一致。

| 语言与策略 | 加载及内置预热 | 首请求 | 3 次热请求中位数 | 生成的思考 token | 译文 token |
| --- | ---: | ---: | ---: | ---: | ---: |
| 英语，完整思考 | 1173.2 ms | 3742.1 ms | 3746.5 ms | 282 | 11 |
| 英语，空思考前缀 | 1187.1 ms | 176.5 ms | 166.7 ms | 0 | 10 |
| 日语，完整思考 | 1184.2 ms | 1776.0 ms | 1756.6 ms | 119 | 13 |
| 日语，空思考前缀 | 1344.5 ms | 182.6 ms | 178.5 ms | 0 | 10 |

以上为 LLM 调用总耗时，不含 ASR、VAD 或等待断句。EOS 各另计 1 个 token；前后的空白及控制标记归属不同，不能由译文 token 数推断内容是否相同。

英语均输出 `Let's meet at three o'clock this afternoon.`。日语完整思考输出 `今日は今午後3時に会議を開く。`，空思考输出 `午後三点に会議を開きます。`，后者没有显式保留「今天」。这里记录输出差异，不宣称翻译质量等价，也不将单条短句的倍数外推为所有请求的加速比。

## 新版连续输入验证

服务端将 CPU 收音、VAD 与单个 GPU 推理工作线程分开。VAD 切出的语音拥有独立缓冲，原始 PCM 窗口随即释放，等待翻译期间可继续对后续采样断句。待处理语音按 120 秒及 64 段双重限制，包含正在推理的段；达到上限返回 `processing_backlog_full`，不丢弃未完成音频后报告成功。

使用与旧版复现完全相同的密集短句音频，按 100 ms 消息、1 倍实时速率发送。新版默认空思考策略收到 22 段原文、22 段英文译文，无错误；每段原文先于同段译文，`queue_wait` 均为 0 ms（日志精度为毫秒）。`done.duration_ms=60037`，与实际提交采样数一致，包含最后不足 100 ms 的 37 ms 尾块。首段原文和译文分别在 2.769、2.966 秒收到，最后完成事件在 60.589 秒收到，没有逐句增加的等待趋势。

这是组合改动的真实 GPU 验证；慢推理期间 VAD 持续消费、断开后等待在途工作结束及积压上限另用受控后端测试，不能仅凭默认翻译变快将所有效果归因于线程调整。用户当时的麦克风及完整现场录音尚未复现；新日志可按阶段查看接收音频时长、墙钟时长、原始队列、VAD 保留窗口、推理排队和各模型耗时。

连续回放事件见 `stream-after-dense60s-20261101.jsonl`，汇总见 `stream-after-dense60s-summary-20261101.json`。诊断字段和错误恢复方式见 [实时接口说明](streaming.md)。

另按实时速率发送 35 秒连续语音，仅识别模式得到 `max_duration`、`max_duration`、`final` 三段，确认两次 15 秒强制断句及尾段冲刷，`done.duration_ms=35000`，无译文事件或错误。2.23 秒快速多词语音加 2 秒静音，用 20 ms 消息翻译为日语，得到 1 段原文和译文，翻译耗时 275 ms，`done.duration_ms=4230`，原文和译文均在 `finish` 前收到。旧文件上传翻译接口也返回 `200`。

`cargo test --workspace --all-targets --locked` 共 69 项通过、4 项本地模型测试默认跳过；工作区严格 Clippy 和格式检查通过。生产模型线程与收音取消、finish 排空及积压预算采用额外受控回归测试，不需录制麦克风。
